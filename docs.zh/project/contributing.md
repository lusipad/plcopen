# 参与贡献

项目欢迎 bug 修复、测试和文档变更。新行为应从语义合同开始，而不是直接从
实现补丁开始。

## 修改代码前

1. 阅读[项目术语与现状](status.md)。
2. 在 `doc/compliance/` 中找到对应规范文档。
3. 检查现有 ADR 是否已有架构裁决。
4. 新增或找到能证明目标行为的测试。

## 变更路径

| 变更 | 必要证据 |
|---|---|
| Bug 修复 | 复现测试、修复及相关回归门禁 |
| 新行为 | 实现前先批准语义矩阵 |
| 周期输出变化 | KB 登记与回放基线复核 |
| 架构变化 | 既有 ADR 或新增已接受 ADR |
| 文档 | 双语 strict 构建与有效站内链接 |

冻结的 `src/` 旧线只接受 P0 回归修复，新工作通常进入 `core/`。

## Pull Request

每次变更保持窄范围。提交信息就是证据包：目的、约束、验证、已知缺口以及
相关 KB/ADR 引用都应写清。CI 通过不能替代必要的语义裁决或发布授权。

准确命令、提交格式、测试安全红线和评审要求见
[权威贡献指南](https://github.com/lusipad/plcopen/blob/main/CONTRIBUTING.md)。
